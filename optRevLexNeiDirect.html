OptRevLex directly on neighbor lists

How the neighbors model in CpModels.java (model optRevLexNeiDir) generates the simple graphs with a given degree sequence, and posts Codish's OptLex symmetry breaking (reversed form) and the upper off-diagonal connectivity constraint directly on the neighbor lists M, without rebuilding 0/1 adjacency rows: addRevLexRows, addOptRevLexNeiDir, dropLabel and addLargestNeighborAbove.

What changed in this version
  • The input is a degree sequence in increasing order: vertex i has degree deg[i]. Row i has D = max(deg) slots.
  • Simple graphs, fixed layout. Each row lists the neighbors strictly increasing in slots 0 .. deg[i]-1, then zeros fixed by position: 2 5 0 0 (addRevLexRows). The strict order replaces the "all different except 0" constraint, and the fixed zeros replace the degree count.
  • Symmetry breaking compares only vertices of equal degree: only they can swap labels when the degrees are fixed.
  • dropLabel reads the deg[i] neighbor slots in reverse (largest first) and deletes label j+1 only if j is a neighbor (e = 1).
  • Connectivity is M[i][deg[i]-1] > i+1 (last neighbor slot = largest neighbor), used by both optRevLexNei and optRevLexNeiDir. It is correct for regular sequences only (section 7).

1. The constraint we want

In the adjacency model, OptRevLex says: for every pair of vertices i < j with deg[i] = deg[j], compare row i and row j with columns i and j deleted, reading the columns right to left (right-most column most significant). Row i must be ≤ row j.

The pair restriction comes from the fixed degree sequence: swapping two vertices of different degrees would break deg, so it is not a symmetry, and ordering such rows would lose graphs.

The neighbors model has no 0/1 rows. Row M[i] holds the neighbors of i as 1-based labels, with 0 for an empty slot. addOptRevLexNei rebuilds the 0/1 rows with count expressions, the same reasoning as Adj. addOptRevLexNeiDir works on the labels themselves.

2. Row layout: one row per neighbor set

/** OptRevLex layout: the neighbors strictly increasing in slots 0..deg[i]-1, then 0: 2 5 0 0. */
private static void addRevLexRows(IloCP cp, IloIntVar[][] M, int[] deg) throws IloException {
    for (int i = 0; i < M.length; i++) {
        int D = M[i].length, last = deg[i] - 1;    // last neighbor slot
        for (int k = deg[i]; k < D; k++) cp.add(cp.eq(M[i][k], 0));
        if (deg[i] > 0) cp.add(cp.ge(M[i][0], 1));
        for (int k = 0; k < last; k++) cp.add(cp.lt(M[i][k], M[i][k + 1]));
    }
}

Why this is enough for a simple graph.

  • Degree. The zeros sit in the last D − deg[i] slots and the first neighbor is ≥ 1, so with the strict order every neighbor slot is ≥ 1: row i holds exactly deg[i] neighbors. No count of zeros is needed.
  • No multi-edge. The neighbors are strictly increasing, so no label appears twice. No all-different is needed.
  • No loop, undirected. Posted by the base model: M[i][k] ≠ i+1 and count(M[u], v+1) = count(M[v], u+1).
  • One row per set. A neighbor set has exactly one strictly increasing listing, so the slot order adds no solutions.

3. Why it can be done on the lists

  1. Deleting columns i and j is deleting two labels. From row i, the deleted cells are A[i][i]=0 and A[i][j]. From row j, they are A[j][i] and A[j][j]=0. What remains are the sets
    S_i = N(i) \ {j} S_j = N(j) \ {i}
    So: remove label j from list i, and label i from list j, but only when i and j are adjacent; otherwise there is nothing to remove.
  2. The right-to-left 0/1 order is a "largest difference" rule. Reading right to left, the first column where the rows differ is the largest element of Si Δ Sj. Row i ≤ row j iff the sets are equal or that element is in Sj.
  3. A decreasing list gives the same rule. Write each set in decreasing order, followed by zeros. Compare left to right: the first position where they differ holds the largest element of the symmetric difference, and the list holding it is the larger one. 0 is smaller than every label, so the padding never decides wrongly. Both lists have the same length, because deg[i] = deg[j].

Conclusion: for every i < j with deg[i] = deg[j],

dec(N(i) − label j+1) ≤lex dec(N(j) − label i+1)

The stored neighbor slots are increasing, so the decreasing list is just those slots read backwards (reverse). The only work left is deleting one label with a fixed number of slots, and that is what dropLabel does.

4. addOptRevLexNeiDir

private static void addOptRevLexNeiDir(IloCP cp, IloIntVar[][] M, int[] deg) throws IloException {
    int n = deg.length;
    if (n < 3) return;
    for (int i = 0; i < n; i++) {
        for (int j = i + 1; j < n; j++) {
            if (deg[i] != deg[j] || deg[i] == 0) continue;
            IloIntExpr e = cp.count(M[i], j + 1);   // = count(M[j], i+1), by symmetry
            // decreasing lists: the increasing neighbor slots 0..deg-1, reversed
            IloIntExpr[] li = reverse(slots(M[i], 0, deg[i])), lj = reverse(slots(M[j], 0, deg[j]));
            cp.add(cp.lexicographic(dropLabel(cp, li, j + 1, e), dropLabel(cp, lj, i + 1, e)));
        }
    }
}
  • Indices vs labels. Vertices are 0-based in the code (i, j), labels stored in M are 1-based: vertex j appears in a list as j + 1.
  • Equal degrees only. Pairs of different degrees are skipped (section 1). Pairs of degree 0 are skipped too: both lists are empty, so there is nothing to compare.
  • Only the neighbor slots. slots(M[i], 0, deg[i]) takes the deg[i] neighbor slots; the trailing zeros are the same in both rows and are left out.
  • One e per pair. e is 1 iff j is in the list of i; the graph is undirected, so it is also 1 iff i is in the list of j. Both deletions share it.
  • Size. At most n(n−1)/2 pairs, each building 2·deg expressions. No new decision variables are created.

5. dropLabel

private static IloIntExpr[] dropLabel(IloCP cp, IloIntExpr[] L, int label, IloIntExpr e)
        throws IloException {
    int d = L.length;
    IloIntExpr[] out = new IloIntExpr[d];
    for (int k = 0; k < d; k++) {
        IloIntExpr shift = cp.prod(e, cp.le(L[k], label));
        IloIntExpr next = (k + 1 < d) ? L[k + 1] : cp.constant(0);
        out[k] = cp.sum(L[k], cp.prod(shift, cp.diff(next, L[k])));
    }
    return out;
}

A CP model can't delete an element at an unknown position, so dropLabel builds each output slot as an expression:

out[k] = L[k] + sk · (L[k+1] − L[k]) sk = e · [L[k] ≤ label] L[d] = 0

This reads as: if sk = 1, take the next slot L[k+1]; otherwise keep L[k].

Why sk = e · [L[k] ≤ label] is the right test

  • L is decreasing. If the label is in the list (e = 1), everything before it is larger, and the label and everything after it are ≤ label. So L[k] ≤ label means "the label is at slot k or earlier", which is exactly the set of slots that move one step left. A 0 enters at the end.
  • If the label is not in the list (e = 0), nothing moves: sk = 0 for all k and the output is L itself. Only an adjacent label is ever deleted.
  • cp.le(L[k], label) is a constraint, but in CP Optimizer a constraint is also a 0/1 expression (IloConstraint extends IloIntExpr), so it can be multiplied.

7. Upper off-diagonal connectivity on the lists

In the adjacency model, every vertex i < n−1 must have at least one neighbor with a larger label: the part of row i to the right of the diagonal is not all zero.

modelmethodconstraint (0-based i)size
optRevLexAdjaddUpperOffDiagonal sum(M[i][i+1 .. n-1]) > 0n − 1 sums
optRevLexNei, optRevLexNeiDiraddLargestNeighborAbove M[i][deg[i]-1] > i + 1n − 1 unary constraints
private static void addLargestNeighborAbove(IloCP cp, IloIntVar[][] M, int[] deg) throws IloException {
    for (int i = 0; i < M.length - 1; i++) {
        int last = Math.max(deg[i] - 1, 0);   // deg 0: slot 0 holds 0, so the constraint fails
        cp.add(cp.gt(M[i][last], i + 1));
    }
}
  • Why one slot is enough. "Some neighbor is larger than i+1" is the same as "the largest neighbor is larger than i+1". The neighbors are increasing, so the largest is the last neighbor slot, deg[i]-1.
  • Not slot 0. Slot 0 holds the smallest neighbor; requiring it above i would require all neighbors above i, and gives no graph at all.
  • Pruning. It is a bound on a single variable: the solver removes 0..i+1 from the domain of M[i][deg[i]-1] before search starts. On 4-regular graphs with n = 12 it is about 3× faster than the count-based sum (3.7 s vs 12.0 s).
  • Only with OptRevLex, so the OptLex models are not run with connectivity.

Correct for regular sequences only

The constraint relies on choosing a labelling where every vertex but the last has a larger neighbor. With a regular sequence any vertex can take any label, so such a labelling always exists for a connected graph. With unequal degrees, only equal-degree vertices can swap labels, and some connected graphs have no such labelling. Example: K2,3 with deg = [2, 2, 2, 3, 3]. The two degree-3 vertices are labels 4 and 5, not adjacent, both with row 1 2 3: M[4][2] = 3 > 4 fails, and swapping 4 and 5 does not help. The program posts the constraint for every sequence anyway: counts are correct for regular sequences and may be too low for non-regular ones.

Checked by brute force on all graphic sequences with n ≤ 6: with connectivity on, Adj / Nei / NeiDir agree on every sequence, and are exact for every regular one; 7 of the 72 sequences, all non-regular, lose connected graphs. Connected regular counts: 2 for n = 6, d = 3; 14 for n = 8, d = 3; 13 for n = 8, d = 4; 81 for n = 9, d = 4; 129 for n = 10, d = 3.

8. Two shortcuts that lose graphs

"Drop j from row i, i from row j" on the 0/1 rows

On the 0/1 rows the columns are positions. Dropping column j from row i keeps column i, and dropping column i from row j keeps column j. Between i and j the two rows then compare different columns. For i = 2, j = 4, n = 5:

position1234
row 2 without col 4col 1col 2col 3col 5
row 4 without col 2col 1col 3col 4col 5

In the lists, i and j are values, so deleting them never shifts the meaning of a slot.

Replacing the label by 0 in place

An earlier variant replaced label j+1 by 0 where it stood (row[k] · [row[k] ≠ j+1]) instead of deleting it. The 0 then stays in the middle of the list, so two lists are compared slot by slot at shifted positions. Tested, it lost graphs in 56 of the 72 graphic sequences with n ≤ 6, even the 5-cycle (0 solutions instead of 1). dropLabel finds exactly the same solutions as addOptRevLexNei.
