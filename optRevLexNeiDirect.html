OptRevLex directly on neighbor lists

How the neighbors model in CpModels.java (model optRevLexNeiDir) generates the simple graphs with a given degree sequence, and posts Codish's OptLex symmetry breaking (reversed form) and the upper off-diagonal connectivity constraint directly on the neighbor lists M, without rebuilding 0/1 adjacency rows: buildRevLexNeighborsModel, addOptRevLexNeiDir, dropLabel and addLargestNeighborAbove.

What changed in this version
  • The input is a degree sequence in increasing order: vertex i has degree deg[i]. Row i has D = max(deg) slots.
  • Simple graphs, layout in the domains. Each row lists the neighbors strictly increasing in slots 0 .. deg[i]-1, then zeros: 2 5 0 0 (buildRevLexNeighborsModel). The zero slots are created with domain {0} and the neighbor slots with domain {1..n} minus the vertex's own label, so placing the zeros, "neighbor ≥ 1" and "no self-loop" need no constraint. The strict order replaces the "all different except 0" constraint, and the fixed zeros replace the degree count.
  • Symmetry breaking compares only vertices of equal degree: only they can swap labels when the degrees are fixed.
  • Drop, then RevLex. For each equal-degree pair, dropLabel removes the slot holding j+1 from row i and the slot holding i+1 from row j (if found); the two rows are then compared with RevLex. It works on the whole rows and needs no adjacency indicator.
  • Connectivity is M[i][deg[i]-1] > i+1 (last neighbor slot = largest neighbor), used by optRevLexNeiDir. It is correct for regular sequences only (section 7).

1. The constraint we want

In the adjacency model, OptRevLex says: for every pair of vertices i < j with deg[i] = deg[j], compare row i and row j with columns i and j deleted, reading the columns right to left (right-most column most significant). Row i must be ≤ row j.

The pair restriction comes from the fixed degree sequence: swapping two vertices of different degrees would break deg, so it is not a symmetry, and ordering such rows would lose graphs.

The neighbors model has no 0/1 rows. Row M[i] holds the neighbors of i as 1-based labels, with 0 for an empty slot. addOptRevLexNeiDir posts the same order directly on the labels.

2. Row layout: one row per neighbor set

/** OptRevLex neighbor rows: the first deg[i] slots hold the neighbors, strictly increasing, then 0: 2 5 0 0. */
private static IloIntVar[][] buildRevLexNeighborsModel(IloCP cp, int[] deg) throws IloException {
    int n = deg.length, D = maxDegree(deg);
    IloIntVar[][] M = new IloIntVar[n][D];
    for (int i = 0; i < n; i++) {
        for (int k = 0; k < D; k++) M[i][k] = (k < deg[i]) ? neighborVar(cp, n, i) : cp.intVar(0, 0);
        for (int k = 0; k + 1 < deg[i]; k++) cp.add(cp.lt(M[i][k], M[i][k + 1]));
    }
    addUndirected(cp, M);
    return M;
}

/** A neighbor slot of vertex i: domain {1..n} without i's own label i+1 (no self-loop). */
private static IloIntVar neighborVar(IloCP cp, int n, int i) throws IloException {
    int[] labels = new int[n - 1];
    for (int v = 1, k = 0; v <= n; v++) if (v != i + 1) labels[k++] = v;
    return cp.intVar(labels);
}

Why this is enough for a simple graph.

  • Degree. The last D − deg[i] slots are created as 0 and the others can only hold labels 1..n, so row i holds exactly deg[i] neighbors. No count of zeros is needed.
  • No multi-edge. The neighbors are strictly increasing, so no label appears twice. No all-different is needed.
  • No loop. Label i+1 is not in the domain of row i's neighbor slots.
  • Undirected. addUndirected: count(M[u], v+1) = count(M[v], u+1).
  • One row per set. A neighbor set has exactly one strictly increasing listing, so the slot order adds no solutions.

3. Why it can be done on the lists

  1. Deleting columns i and j is deleting two labels. From row i, the deleted cells are A[i][i]=0 and A[i][j]. From row j, they are A[j][i] and A[j][j]=0. What remains are the sets
    S_i = N(i) \ {j} S_j = N(j) \ {i}
    So: remove label j from list i, and label i from list j, if they appear. They appear in both lists or in neither (the graph is undirected).
  2. The right-to-left 0/1 order is a "largest difference" rule. Reading right to left, the first column where the rows differ is the largest element of Si Δ Sj. Row i ≤ row j iff the sets are equal or that element is in Sj.
  3. A decreasing list gives the same rule. Write each set in decreasing order, followed by zeros. Compare left to right: the first position where they differ holds the largest element of the symmetric difference, and the list holding it is the larger one. 0 is smaller than every label, so the padding never decides wrongly. Both lists have the same length, because deg[i] = deg[j].

Conclusion: for every i < j with deg[i] = deg[j], drop then compare:

reverse(M[i] without j+1) ≤lex reverse(M[j] without i+1)

The rows list the neighbors increasing, so reading them from the last slot (reverse) gives the decreasing lists of point 3. The fixed zeros are in the same slots of both rows (equal degrees), so they never decide.

4. addOptRevLexNeiDir

private static void addOptRevLexNeiDir(IloCP cp, IloIntVar[][] M, int[] deg) throws IloException {
    int n = deg.length;
    if (n < 3) return;
    for (int i = 0; i < n; i++) {
        for (int j = i + 1; j < n; j++) {
            if (deg[i] != deg[j]) continue;
            IloIntExpr[] ri = dropLabel(cp, M[i], j + 1);   // row i without j+1
            IloIntExpr[] rj = dropLabel(cp, M[j], i + 1);   // row j without i+1
            cp.add(cp.lexicographic(reverse(ri), reverse(rj)));
        }
    }
}
  • Indices vs labels. Vertices are 0-based in the code (i, j), labels stored in M are 1-based: vertex j appears in a row as j + 1.
  • Equal degrees only. Pairs of different degrees are skipped (section 1).
  • Drop, then RevLex. Each row loses the slot of the other vertex, if found; then cp.lexicographic on the reversed rows compares them from the last slot.
  • Size. At most n(n−1)/2 pairs, each building 2·D expressions. No new decision variables are created.

5. dropLabel

private static IloIntExpr[] dropLabel(IloCP cp, IloIntExpr[] row, int label) throws IloException {
    int D = row.length;
    IloIntExpr[] out = new IloIntExpr[D];
    IloIntExpr atOrBefore = cp.constant(0);   // [k ≤ p]
    for (int k = D - 1; k >= 0; k--) {
        atOrBefore = cp.sum(atOrBefore, cp.eq(row[k], label));
        IloIntExpr prev = (k > 0) ? row[k - 1] : cp.constant(0);
        out[k] = cp.sum(row[k], cp.prod(atOrBefore, cp.diff(prev, row[k])));
    }
    return out;
}

Let p be the slot of the label in the row. A CP array has a fixed length and p is not known while the solver searches, so the slot can't be removed directly. Instead every output slot says which input slot it takes:

out[k] = row[k−1] if k ≤ p, else row[k] (row[−1] = 0)

The slots before p move one step right and a 0 enters slot 0. Example: 2 5 0 0 without 5 (p = 1) → 0 2 0 0.

How the test [k ≤ p] is built

  • A count from the right. [row[k] = label] + … + [row[D−1] = label] is 0 after the label and 1 from the label down to slot 0: exactly [k ≤ p]. A label appears at most once in a row (strict order).
  • If not found. Every term is 0, so the row is unchanged: no adjacency indicator is needed. i and j are adjacent in both rows or in neither, so both rows lose a slot or neither does.
  • Why not compute p as a number. p = Σ (k+1)·[row[k] = label] − 1 and then [k ≤ p] gives the same solutions, but propagates worse: 20.5 s instead of 15.0 s on 4-regular graphs with n = 12 (76 s instead of 39 s for OptLex).
  • Why the 0 enters at the front. RevLex compares from the last slot, so the freed slot must be at the front: it is then the last slot compared, and it is in the same place in both rows. Shifting the other way (0 at the end) gives the same solutions but the freed slot is compared first, and the run takes 104.9 s instead of 15.0 s.
  • OptLex uses the same dropLabel. Its rows are the mirror image (0 0 5 2: zeros, then neighbors decreasing) and are also compared from the last slot, so the freed slot must be at the front too. Example: 0 0 5 2 without 5 → 0 0 0 2.
  • cp.eq(row[k], label) is a constraint, but in CP Optimizer a constraint is also a 0/1 expression (IloConstraint extends IloIntExpr), so it can be summed and multiplied.

7. Upper off-diagonal connectivity on the lists

In the adjacency model, every vertex i < n−1 must have at least one neighbor with a larger label: the part of row i to the right of the diagonal is not all zero.

modelmethodconstraint (0-based i)size
optRevLexAdjaddUpperOffDiagonal sum(M[i][i+1 .. n-1]) > 0n − 1 sums
optRevLexNeiDiraddLargestNeighborAbove M[i][deg[i]-1] > i + 1n − 1 unary constraints
private static void addLargestNeighborAbove(IloCP cp, IloIntVar[][] M, int[] deg) throws IloException {
    for (int i = 0; i < M.length - 1; i++) {
        int last = Math.max(deg[i] - 1, 0);   // deg 0: slot 0 holds 0, so the constraint fails
        cp.add(cp.gt(M[i][last], i + 1));
    }
}
  • Why one slot is enough. "Some neighbor is larger than i+1" is the same as "the largest neighbor is larger than i+1". The neighbors are increasing, so the largest is the last neighbor slot, deg[i]-1.
  • Not slot 0. Slot 0 holds the smallest neighbor; requiring it above i would require all neighbors above i, and gives no graph at all.
  • Pruning. It is a bound on a single variable: the solver removes 0..i+1 from the domain of M[i][deg[i]-1] before search starts.
  • Only with OptRevLex, so the OptLex models are not run with connectivity.

Correct for regular sequences only

The constraint relies on choosing a labelling where every vertex but the last has a larger neighbor. With a regular sequence any vertex can take any label, so such a labelling always exists for a connected graph. With unequal degrees, only equal-degree vertices can swap labels, and some connected graphs have no such labelling. Example: K2,3 with deg = [2, 2, 2, 3, 3]. The two degree-3 vertices are labels 4 and 5, not adjacent, both with row 1 2 3: M[4][2] = 3 > 4 fails, and swapping 4 and 5 does not help. The program posts the constraint for every sequence anyway: counts are correct for regular sequences and may be too low for non-regular ones.

Checked by brute force on all graphic sequences with n ≤ 6: with connectivity on, Adj / Nei / NeiDir agree on every sequence, and are exact for every regular one; 7 of the 144 sequences, all non-regular, lose connected graphs. Connected regular counts: 2 for n = 6, d = 3; 14 for n = 8, d = 3; 13 for n = 8, d = 4; 81 for n = 9, d = 4; 129 for n = 10, d = 3.

8. Two shortcuts that lose graphs

"Drop j from row i, i from row j" on the 0/1 rows

On the 0/1 rows the columns are positions. Dropping column j from row i keeps column i, and dropping column i from row j keeps column j. Between i and j the two rows then compare different columns. For i = 2, j = 4, n = 5:

position1234
row 2 without col 4col 1col 2col 3col 5
row 4 without col 2col 1col 3col 4col 5

In the lists, i and j are values, so deleting them never shifts the meaning of a slot.

Replacing the label by 0 in place

An earlier variant replaced label j+1 by 0 where it stood (row[k] · [row[k] ≠ j+1]) instead of deleting it. The 0 then stays in the middle of the list, so two lists are compared slot by slot at shifted positions. Tested, it lost graphs in 56 of the 144 graphic sequences with n ≤ 6, even the 5-cycle (0 solutions instead of 1). dropLabel finds exactly the same solutions as optRevLexAdj.
